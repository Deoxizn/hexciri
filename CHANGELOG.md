# Changelog

## 2026-09-08+ — hexciri v1.5 (omarchy-edge kernels + AUR 580xx)

- **Kernels come from the omarchy edge repo on bleeding** — `pacman-bleeding.conf` ships `[omarchy]` → `https://pkgs.omarchy.org/edge/$arch` (omarchy-keyring bootstrapped on install when the deployed conf carries the repo). `System ▸ Kernel` offers Stock, LTS, `linux-omarchy` (EEVDF) and `linux-omarchy-bore` (BORE); `hexciri-scheduler` recommends BORE for NVIDIA/X3D else EEVDF. Because they are ordinary repo packages they update with plain `pacman -Syu` — no fetch loop, no AUR rebuild. Stable stays stock/lts only (vetted repo); omarchy kernels are a bleeding extra.
- **Legacy 580xx installed from the AUR** — the driver went EOL in official Arch repos when the 590 release dropped below Turing (the line now lives on AUR), so `hexciri-gpu`'s legacy branch builds the `nvidia-580xx` split (`nvidia-580xx-utils` → `-dkms` → `lib32-utils` → opencl → lib32-opencl) in dependency order as a regular user: temporary passwordless-pacman sudoers rule, import of the signing keys (`E18447AC…`, `E8B9AA39…`), `makepkg -si` per package, `--skippgpcheck` fallback if the keyserver is unreachable, rule removed after. Updates ride the existing `yay -Sua` pass, so `hexciri-update` has no separate driver-refresh loop.
- **The legacy install bug that broke Pascal/Volta boxes is fixed** — during stage2 install a resolver never found the driver-fetch helper (it only exists under `/root/hexciri-install/bin/` inside the chroot), so the 580xx was silently skipped, nothing NVIDIA was ever installed, and those cards booted into nouveau, which hard-locks after login — confirmed on the 1080 Ti box. The AUR build now lives entirely inside `hexciri-gpu` and works in the chroot; `verify_nvidia_mod` still refuses to green-light a boot back to nouveau.
- **The Config menu knows the split WM trees** — one row per niri fragment (config/env/input/autostart/monitors/looknfeel/window-rules/keybinds/cursors) plus dir-level edits for the hypr/sway/mango trees.
- **Strata's system file chooser is on by default** — strata is the default file manager, so `hexciri-strata-install` runs `strata --install-portal` at provision time (and repairs it on any login `--check` where the metadata is missing) instead of leaving Open/Save dialogs to a desktop chooser that may not exist here.
- `hexciri-sync`/`hexciri-gaming` kernel lists, starship OS-symbol maps, installer comments, README channel table and CHANGELOG now describe the omarchy kernel line.

## 2026-09-08 — hexciri v1.4

- **Esc in submenus now goes back, not away** — Share, System ▸ Default Apps, System ▸ Kernel, and Restart each *exited outright* when you pressed Esc (Share even jumped to the Hardware menu instead of returning). Every dmenu stage now re-execs its parent menu: Share → root, Default Apps → System (each category picker → the Defaults list), Kernel → System, Restart → root.
- **Legacy NVIDIA no longer forces the LTS kernel** — the earlier "580xx only survives LTS" assumption is wrong: the 580 legacy line is the last for Maxwell/Pascal/Volta, but NVIDIA keeps new-kernel compatibility fixes in it for the product lifetime, and recent 580xx DKMS builds run on mainline 7.x. `hexciri-scheduler` again follows the plain BORE (dGPU/X3D) vs EEVDF rule, `hexciri-gpu` installs the 580xx stack on whatever kernel is picked (respecting the boot default, stock fresh-install default — no pin, no refusal), and the installer stages stock linux unless `--kernel=lts` is explicit.
- **580xx builds from the AUR, not a repo** — the driver went EOL in official Arch repos when the 590 release dropped below Turing (the line now lives on AUR). `hexciri-gpu`'s legacy autodetect builds the `nvidia-580xx` split in dependency order as a regular user, and `hexciri-update` covers it via the normal AUR pass.
- **fastfetch header is just `► Hexciri`** — the old row hard-coded a `SOLO` module key and printed `► Hexciri - Arch × Niri × Noctalia`. The `- Arch × $wm × $sh` tail was dropped (the WM/shell combo is live config, not branding) and the row became a `custom` module, so the stray `SOLO:` label is gone too.
- **systemd-boot renders at full console resolution** — hexciri-sync stamps `console-mode max` into `/boot/loader/loader.conf` (preserving a user-set `console-mode` if present). Fixes the ~1 inch tall boot-menu text on high-density/GOP consoles.
- **Kernel selection references cleaned out of the installer** — the Kernel menu is the one selectable kernel path; fresh installs are always stock. `--kernel stock|lts` remains parseable (internal/support use only), but bootstrap's info line, the usage comment, and the README kernel row no longer advertise it as a selectable install option.

- **System ▸ Config ▸ Hexciri Lockscreen sets the panel-off re-arm delay** — new `~/.config/hexciri/lockscreen.conf` (`lock_panel_delay`, seconds; `0` = leave monitors on while locked) is seeded on first open of that Config entry and read fresh on every lock. It's the knob behind the 20s "panels go dark again" default.
- **Every Update press now re-applies sync state** — the alpm hook only fired when a tracked package (kernel/sddm/…) actually changed, so a no-op update never ran `hexciri-sync` and no `/etc/makepkg.conf.d/hexciri-tuning.conf` appeared on machines that had nothing to upgrade. `hexciri-update` now runs `sudo hexciri-sync` explicitly after the transaction — boot entries, PAM, the gnome-keyring pin, and the per-PC makepkg tuning land on every press. (The hook still covers plain `pacman -Syu`.)
- **`hexciri-scheduler` auto-detects the best scheduler from this machine** (per request: run at install AND on kernel change): reads sysfs (NVIDIA dGPU → interactive), `model name` (`X3D` → gaming cache), `/proc/meminfo` RAM, and battery supply (laptop) to recommend **BORE** for gaming/interactive or **EEVDF** otherwise (a server-profile note is surfaced, never auto-applied). `detect` is read-only and non-destructive; `run` executes the pick through the kernel flow. The System ▸ Kernel **Recommended** row and the fresh-install output both use it.
- **Bleeding channel is now plain official Arch** — `mirrorlist-bleeding` points at `geo.mirror.pkgbuild.com` and the `[omarchy]` edge repo is dropped from `pacman-bleeding.conf`; `hexciri-channel-current` reads the mirror feed alone. **Stable keeps its purpose** — the omarchy month-hold mirror plus the `[omarchy]` repo (real packages: 1password, asusctl, claude-code, …) stay for users who want slower, vetted releases. `install.sh` bootstraps `omarchy-keyring` only when the deployed channel config still has `[omarchy]` (gated by the file, so bleeding skips it).
- **Per-PC makepkg tuning (`lib/makepkg-tuning.sh`)** — writes `/etc/makepkg.conf.d/hexciri-tuning.conf` (jobs = `nproc`, CFLAGS/CXXFLAGS matched to the detected CPU tier: `znver4`/`x86-64-v4`/`x86-64-v3`, distro default untouched on generic). Official repo packages are prebuilt and unaffected; local/AUR builds get the machine's tier. Runs on fresh installs **and** on every existing machine via `hexciri-sync`'s alpm-hook pass (FIX POLICY: fresh + existing get the same fix).
- **install.sh sheds the dead omarchy flow**: `--kernel` is now `stock|lts` only (custom kernels are verifiably post-install personalization via System ▸ Kernel), the single-kernel replace policy block is gone (an update never strips a staged kernel), and the GPU step is followed by a non-destructive scheduler detect pass. Existing-install detection keys off the `hexciri-sync` alpm hook or a present `[omarchy]` repo.
- **`hexciri-lock` powers monitors down on every WM, lock-scoped not idle-scoped** — it previously called `hyprctl dispatch dpms off` for hyprland alone, leaving the default niri WM a no-op (niri supports it via `niri msg action power-off-monitors`, sway via `swaymsg output '*' dpms off`). It now routes through the `hexciri-compositor power-off-monitors` shim so the 20s-after-lock panel-off works on all four WMs.
- **Re-arms every 20s while still locked** — a bump of the mouse/keyboard while locked wakes the panels (niri/Noctalia do that), and 20s later they power back down, guarding against pets/accidental bumps when you look away. It's tied to *time-since-lock*, never to system idle: unlocked sessions are untouched. "Still locked" is read from `noctalia msg status`'s `locked` field; non-noctalia shells get a finite (`~50 min`) cap so a background proc can never run away. (Timing knob: Config ▸ Hexciri Lockscreen, above.)
- **VERSION file matches the git tag** — bumped `0.1.3` → `1.4`, aligning it with the v1.4 release.

## 2026-09-07 — hexciri v1.4 (WM/shell flavoring)

- **Every WM ships a full config tree** — `config/{hyprland→hypr,sway,mango}/` replace the single niri config sprouting per-WM fragments: hyprland (`hyprland.lua` entry + `conf/{env,input,autostart,monitors,looknfeel,window-rules,keybinds}.lua` — the 0.56 native-Lua form, `hl.env`/`hl.config`/`hl.monitor`/`hl.window_rule`), sway (entry + `conf.d/*` include glob + `environment.d/10-hexciri.conf`), mango (entry sourcing 7 `$HOME` sub-configs). `install.sh` deploys the tree matching `--wm`; `hexciri-session-set` swaps by seeding repo defaults for missing files (`seed_wm()`), carrying monitors over, rendering keybinds, and re-applying the theme — leaving user edits untouched (sha-tracked deploy / only-if-missing seed).
- **env/input/autostart now carry across a WM swap like monitors do** — new `bin/hexciri-config-render` renders the three concerns from the **live** `~/.config/niri/{env,input,autostart}.kdl` (the machine's reality, never the repo template) into the target WM's own syntax: niri KDL, **Hyprland Lua** (`hl.env` / `hl.config({input})` / `hl.on("hyprland.start")` per the 0.56 era — validated against the stellarchy remux's `config/hypr/*.lua`), sway (`input type:*` blocks; env has no sway directive, so it lands in `~/.config/environment.d/10-hexciri.conf`), and mango (`env=` / flat input keys / `exec-once=`, split via `source-optional=` sub-configs per the mango docs). Unrenderable niri-only semantics (tap-button-map, click-method, disabled-while-typing edge cases) surface as `# NOTE` comments, never silently dropped — policy §7. `hexciri-session-set` step 4 now runs all three plus the existing monitors copy.
- **Session > Remove finally completes the WM lifecycle** — new `bin/hexciri-session-remove` (System > Session > Remove, or `hexciri-session-remove <wm>`): lists installed (non-current, non-running) WMs, then per pick backs up `~/.config/<wm>` → `.config/hexciri-backup/<ts>-<wm>`, removes the WM's own package set (`pacman -Rns` — shared deps like xwayland-satellite are pruned as orphans, never yanked from under another WM), and deletes `/usr/share/wayland-sessions/<wm>.desktop`. Refuses the active selector WM and the currently-running compositor. Menu: Session is now a submenu (`hexciri-session-menu`) — **Install >** (the existing picker) and **Remove >** (installed list), Esc returns to System.
- **Mango keybinds were being shipped as dead `=`-syntax** — `hexciri-keybinds-render mango` emitted `bind=SUPER,K=exec cmd`-style lines the WM would never read. Mango's real format is `bind=[flags]MODS,KEY,COMMAND,PARAMS` (dwl heritage). Rewrote `key_mango` (SUPER/CTRL/ALT/SHIFT packing) and the mango branch: spawn commands with shell metachars reroute to `spawn_shell`, and the intents' mango actions were corrected to real mango dispatchers — `view N` (show tag N), `tag N` (send client to tag N), `killclient`, `viewtoleft/right` — while the no-sibling semantics (directional focus/move, maximize, fullscreen → fakefullscreen, float) now render as visible `# (See NOTE)` comments instead of wrong binds. Package in install.sh corrected from the nonexistent `mango` to the AUR `mangowm`.
- **The compositor is now a pluggable choice, not a niri assumption**: every IPC call in the framework goes through a shim — `bin/hexciri-compositor` (`screenshot/load-config/quit/lock/outputs-json/window-id-for`) and `bin/hexciri-session` (resolves `wm`+`shell` from `~/.config/hexciri/{wm,shell}` with `XDG_CURRENT_DESKTOP` fallback, knows the shipped set `niri|hyprland|sway|mango` × `noctalia|none`). All former raw `niri msg` callers (capture, screenrecord, launch-or-focus-webapp, restart, toggle-input-device, power, lock) route through the shim, which dispatches per active WM — hyprland/sway get their native equivalent, anything without IPC is a graceful no-op.
- **Deliberate WM swap from the menu**: **System > Session** runs `hexciri-session-set` — pick the target combo (args like `wm=hyprland` or the fuzzel picker), it pulls-fresh + re-execs (same guard as the updater funnel), installs the WM package + guarantees a `/usr/share/wayland-sessions/<wm>.desktop` login entry, carries over the real monitor layout (niri output-block ↔ hyprland `monitor =` line ↔ sway output translation, whole-file per design), writes the selector, then re-renders the theme + keybinds. Current session is untouched — you log out and pick the new WM in sddm, which is exactly where the choice was always supposed to live.
- **install.sh takes `--wm` + `--shell`**: package list, session file, and the deployed config all follow the pick (`config/<wm>/` for the chosen compositor; `config/noctalia/config.toml` only when a shell is picked). The selector file (`~/.config/hexciri/{wm,shell}`) is written at install so the runtime always agrees with what was installed. `niri`/`noctalia` remain the defaults — every existing invocation behaves exactly as before. The shipped shell set is just `noctalia` (and `none`, no-shell); anything beyond that is a future possibility, not a promise.
- **The niri config is a true per-concern split** (`config/niri/…`): `config.kdl` became an entry that only includes the fragments (`cursors.kdl`, `env.kdl`, `monitors.kdl`, `input.kdl`, `looknfeel.kdl`, `window-rules.kdl`, `keybinds.kdl`, `autostart.kdl`) plus the static niri globals — cursor and input settings moved to their own fragments, animations moved into `looknfeel.kdl` (the "feel" half of look-and-feel), and the hotkey overlay now properly skips at startup on every machine. The theme hook deploys `cursors.kdl` + `input.kdl` too; `sync.sh` and `install.sh` learn the new fragment list.
- **Theme hook generalizes to every WM** (`hooks/theme-set.d/noctalia-sync.sh` → `hexciri-sync.sh`): the WM-independent render (Noctalia palette + config.toml, qt6ct scheme, wallpaper) is unchanged, but the niri-only border patch became a per-WM loop — hyprland `col.active_border/inactive_border`, sway `client.focused/unfocused`, plus Noctalia's own `noctalia.kdl` include are all written when the corresponding config exists. Boot Sway after configuring niri and the borders are still right.
- **Keybinds are single-source**: `config/keybinds/intents.toml` is the schema (one row per intent: combo → intent name), with two render paths — `hexciri-keybinds` (searchable reference for the active WM) and `hexciri-keybinds-render <wm>` (emits the WM's `binds {}`-style block, seed for `config/niri/keybinds.kdl`). Muscle memory survives a WM change because the schema, not each config, is maintained.
- **fastfetch follows the session**: the brand line and WM row read the `~/.config/hexciri/{wm,shell}` selector at render time — `Niri 26.04 | Noctalia 5.0.1` today, `Sway | none` after a swap; no hardcoded compositor in the banner.
- **Splitting keeps your history**: a legacy pre-split `config.kdl` is backed up byte-for-byte to `config.bak` before the split lands (the theme hook does this on first post-split theme change), so per-machine tweaks are ported from the backup, not lost.
- **Learn lists what's actually installed**: the docs menu now gates each row on `command -v` — uninstall a package and its docs entry disappears (so an opencode you didn't want to keep stops being assumed), and the terminal row follows whichever terminal you have installed. The menu reflects the machine as shipped.
- **The alpm hook refreshes on every system update, even no-op ones**: `hexciri-update` re-applies the hook from the pulled tree right after validating sudo. Previously the hook only self-refreshed while a package transaction actually ran (`hexciri-sync` fires from the hook itself), so an update with nothing to upgrade never re-applied it — a stale hook (missing the `gnome-keyring` target) lingered on boxes that keep coming up empty. A real `Update ▸ Hexciri` press now converges repo, plugin `update_cmd`, **and** the hook in one go.
- **The self-heal now lives in the funnel everyone presses** — `hexciri-update-hexciri` (which `hexciri-update`, `hxup`, and the `Update ▸ Hexciri`/`Update ▸ Repo` menu actions all invoke) now pulls **then re-execs its own freshly-pulled bytes** (guarded `HXC_UPX_RERUN`, one-shot) so the deploy steps — bin re-links, the plugin `update_cmd` migration, whatever ships next — run *in the same press*, not the press after. Previously that "ship AND run" guarantee was bolted onto `hexciri-update` and `hexciri-sync` individually, and the plugin migration sat *after* the interactive "Run system update?" confirm, so `System Update > Hexciri` (the pull-only path) and cancelled updates both silently deferred it. Migration is now unconditional, before any prompt, in every updater (`hexciri-update`, `hexciri-update-hexciri`, and the root alpm `hexciri-sync`, which self-pulls + re-execs on its own).
- **`Update ▸ Hexciri` is the real system updater now** — it dispatches the full `hexciri-update` (repo + AUR + reboot check), matching the `hxup` alias and the noctalia arch-updater plugin, instead of only pulling the framework. The old "System update" entry and the pull-only behavior it duplicates are gone: `Hexciri` = system update, `Repo` = framework pull only. This is the "one press = everything" action from the menu.
- **Self-heal re-exec: a press that ships a fix also *runs* it — no "run it twice"**. Found a hole: the press that pulled `c729f54` was the pre-rename updater's own old bytes, so the plugin `update_cmd` migration (which was *in* the pulled repo) couldn't run that same press, and an up-to-date `pacman -Syu` fired no hook to trigger it either — the fix silently waited for a second press. Both entry points now re-exec from the freshly-pulled tree mid-invocation (guarded `HXC_RERUN`/`HXC_SYNC_RERUN` so only one re-exec, second pass fast-forwards cleanly): `hexciri-update` pulls at the top then `exec`s its pulled self, and `hexciri-sync` (root alpm hook run) re-execs the pulled `$REPO/bin/hexciri-sync` (with `HEXCIRI_REPO` exported so the root pass keeps its repo path). Every future fix that rides the update lands the same press the user presses — one press, walk away.
- **Updater renamed to `hexciri-update`** (was `hexciri-update-run`); the old Update menu is now `hexciri-update-menu`. A zero-fat `hexciri-update-run` shim keeps every stale reference working (noctalia arch-updater plugin `update_cmd`, fish aliases, muscle memory), and both `hexciri-update` and `hexciri-sync` migrate the plugin's stored `update_cmd` to the new name on the next real run — so an existing machine that only clicks "Arch Updater" converges scripts **and** plugin settings in that first update. `hxup` is now the shipped fish alias for it.
- **A system update alone now covers every machine**: `hexciri-sync` self-updates the repo checkout before doing anything (the alpm hook is a symlink into the repo, so a stale checkout previously meant a stale fix — now the hook pulls as the repo owner first), re-applies its own hook file from the pulled tree so newer targets ride along immediately, and when it must downgrade an in-transaction gnome-keyring 50.0 it queues the re-run itself (transient `systemd-run` timer, fallback: detached wait-loop) instead of printing "run sudo hexciri-sync later". So: new installs get `install.sh`, every existing user gets plain `sudo pacman -Syu` — no git pull, no second command. This is the pattern fixes follow from here on: shipped in `install.sh` for fresh installs, mirrored in the sync hook for existing ones.
- **Gnome-keyring popup finally killed — the old fix was dead code**: the version check `grep -q ' 50\.'` could never match `1:50.0-1` (the epoch prefix), so the auto-downgrade to 48.0 never fired on any box — the "Keyring, quiesced" changelog entry was aspirational. Three bugs fixed so installs AND existing machines actually converge: (1) the version probe now matches the epoch form (`grep -qE '[ :]50\.'`); (2) the pin/downgrade block moved **out** of the `if ! $UPDATE_MODE` guard in `install.sh`, so `install.sh --update` re-asserts it instead of skipping it; (3) the real root cause — the `gnome-keyring-daemon.socket` unit ships enabled at GLOBAL scope (`/etc/systemd/user/sockets.target.wants/`), so socket-activation can start the daemon *before* PAM runs and `pam_gnome_keyring`'s `auto_start` loses the race ("another secret service is running") → locked login keyring → unlock popup. The version pin alone can't fix that race; `install.sh`, `hexciri-sync`, and `hexciri-gkr-pin.sh` now also run `systemctl --global disable gnome-keyring-daemon.socket gnome-keyring-daemon.service` so PAM auto_start stays the sole starter. `hexciri-sync` finally downgrades a slipped-in 50.0 instead of just warning (guarded so it can't `pacman -U` from inside an alpm transaction — it defers with a pointer instead of the old bogus `db.lck` that broke the very transaction it ran inside), its alpm hook gained `Target = gnome-keyring`, and the PAM checks in `install.sh`/`hexciri-sync` no longer treat *commented-out* module lines as active (`grep -Ev '^\s*#'`).

## 2026-09-06 — hexciri v0.1.3

- **Install never flips your pacman channel**: install.sh previously re-asserted `/etc/pacman.conf` + mirrorlist for its default `stable` channel on every first-install-style run — so a re-install (or the documented pre-0.1.3 bootstrap) over a box already on `bleeding` silently downgraded the package set (e.g. noctalia stable, which speaks an older settings.toml `config_version` and then rejected the bleeding-written override file, ignoring your wallpaper picker). The channel is now treated as personal state: if hexciri's `[omarchy]` repo is already present, the installer keeps the current channel and only fills in the keyring/sync; `hexciri-channel-set` remains the deliberate way to switch.
- **Repo sync floats on its own**: Update ▸ Repo / Hexciri run in the blur-floated `TUI.float` scratchpad (1000×720) instead of a full workspace terminal — matching the install/remove pattern, so the framework update no longer hijacks the whole screen.
- **Wallpaper sources, with examples**: the shipped `config/wallpaper-sources/extra.list` now shows both `~/` shorthand and absolute paths in real, commented examples (e.g. `~/Pictures/Wallpapers`), and the live per-machine list is (re-)seeded from it on first use.
- **One manual rescan entry**: **Update ▸ Wallpaper** re-runs `hexciri-wallpaper-refresh` on demand — prune every stale `zz-user-*` link and re-link — in the floating window. Newly added store/directory files land immediately, no need to wait for a login or a theme change.
- **Theme swaps keep your picker set**: the refresh no longer auto-fires at login (`hexciri-theme-ensure`), on **Themes ▸ Backgrounds**, or at theme-set — **Update ▸ Wallpaper** is the single trigger. And `hexciri-theme-set` now preserves your `zz-user-*` symlinks across the swap (snapshot → restore around the theme-tree rebuild) instead of wiping them with the re-copied backgrounds dir. The dir-list reader also tolerates files with no trailing newline — previously the final source directory (e.g. an NFS mount) was silently dropped from the merge.
- **Noctalia keeps your wallpaper on theme switch**: the theme-set hook no longer force-applies the theme's default background over your live picker wallpaper while the store holds custom entries — chosen wallpapers survive theme changes.
- **Strata follows the theme live**: Strata's *Follow Omarchy* mode only watches `~/.local/state/omarchy/current`, while hexciri keeps its theme state under `~/.local/state/hexciri/current` — so the option never appeared and Strata's colors only refreshed on restart. `hexciri-theme-ensure` now bridges the two state dirs with a symlink (an unrelated real dir is moved aside first); Strata sees a valid Quattro state at every launch and hot-applies palette changes on each `hexciri-theme-set`, no reopen needed.
- **Your wallpapers survive theme changes**: the active theme's `backgrounds/` dir is a generated snapshot wiped on every theme set, so the picker's folder was a terrible place for personal images. `hexciri-theme-set` now merges every file from a real, persistent user store — `~/.config/hexciri/wallpapers` — into the active backgrounds dir as read-only `zz-user-*` symlinks, so Noctalia's picker lists the theme's shipped set AND all your images at once. Your store is never copied or deleted; the symlinks are by-path only, so entries pointing at an NFS mount that isn't up yet still link now and resolve when the mount appears. The background pick ignores `zz-user-*` so a theme change still applies the theme's own default. **Themes ▸ Backgrounds** now opens the store (created on first use).
- **Black-blank-tile refresh**: a standalone `bin/hexciri-wallpaper-refresh` re-runs the merge without touching the theme — it prunes `zz-user-*` links and re-links from the current store + dirs. Deleting a store file removes its stale link on the next refresh, so the picker stops showing blank placeholder tiles.
- **Directory sources + extra dirs list**: the store can hold directories (plain or symlinked, e.g. an NFS mount) whose images merge flattened as `zz-user-<dirname>-<name>`. A shipped `config/wallpaper-sources/extra.list` (user-overridable at `~/.config/hexciri/wallpaper-sources/extra.list`, one dir path per line, `#` comments and `~/` expansion) adds whole extra directories to the merge — mirrors the themes' `extra.list`, and **Config ▸ Wallpaper dirs list** edits it (seeded from the shipped copy on first open). Removing a line prunes that dir's links on the next refresh; `Config ▸ Omarchy themes list` is dropped — Omarchy defaults are a fixed shipped set, not user-curated.
- **Extra themes list accepts repo paths**: `extra.list` now takes either the literal path you'd paste after `github.com/` (`HANCORE-linux/omarchy-inkypinky-theme`) or the short theme name (`HANCORE-linux/inkypinky`) — the `omarchy-<name>-theme` naming is normalized away so both spell the same theme (full `https://…` URLs still work for repos that don't follow the naming). Clones never prompt for a GitHub account (`GIT_TERMINAL_PROMPT=0`) — a missing/private repo fails visibly instead of hanging on a credential prompt. Fixed a prune bug that removed freshly-installed extras: `rg -q` inside a `pipefail` pipeline died via SIGPIPE (rc 141), so reconcile falsely dropped extras on the same run that installed them; the listed set is now captured once and matched with a here-string.
- **Repo clone is the runtime — updates never re-run install.sh**: commands are flattened into a single `bin/` (the old `scripts/` split is gone) and symlinked to `~/.local/bin` at bootstrap, so the checkout IS the deployment. `hexciri-update-hexciri` (**Update ▸ Repo / Hexciri**, and the framework pass inside `hexciri-update-run`) now just does `git fetch` + `git pull --ff-only`, re-links the command dir (renamed/new commands land instantly), and in one simple pass clears the legacy root hard-copies a pre-symlink install left in `/usr/local/bin` + the `/usr/share/hexciri` mirror (hooked through the system update, which already runs as root) — no install.sh, no sudo on a plain pull, and the Omarchy default themes ride along with the sync (extras stay with **Update ▸ Themes**). A system update (`hxup`/arch-updater → `hexciri-update-run`) stays `pacman -Syu` **plus** the repo pull, and validates sudo before the sync so that cleanup always has root when it's reached that way. install.sh no longer mirrors themes/`.default`/`theme-sources` into `/usr/share/hexciri`; `/usr/share/hexciri` now holds only the root-owned boot-destination pin, and a single `/usr/local/bin/hexciri-sync` symlink keeps the alpm hook live. All theme/version/config helpers now resolve the catalog straight from the repo checkout.
- **Cleaner command naming**: the maintenance menu `hexciri-system-update` is renamed `hexciri-maintenance` so it no longer collides with the updater (`hexciri-update` / `hexciri-update-run`). Renames propagate to existing boxes on their next update/re-link — nothing to migrate by hand.
- **Themes are list-driven**: new `Theme-sources` catalog (`config/theme-sources/`). The shipped Omarchy set (22 themes) is seeded on first install as symlinks to a sparse clone of `omacom/omarchy@quattro`'s `themes/` and kept up to date by the repo sync (`hexciri-update-hexciri` → `hexciri-theme-omarchy`: seed-if-missing, then `git pull` + re-link + prune, non-fatal). A flat `extra.list` (`<owner>/<name>` per line, or a full `https://github.com/…` URL when a repo doesn't follow the naming convention) drives the handpicked set; `hexciri-theme-extras` touches ONLY that extras list — never the Omarchy defaults (which it merely *references* via `is_default` so an extra can't clobber one). The one action — **Update ▸ Themes** — syncs the Omarchy set and clones + `git pull`s + prunes extras to match their lists; deleting a list line uninstalls that theme locally (empty `extra.list` and run it again to clear extras), and **Config ▸ Extra themes list** opens your per-machine `~/.config/hexciri/theme-sources/` override for editing (seeded from the shipped copy on first open). No GitHub account needed: everything is anonymous `git clone`/`pull`. `hexciri-theme-install` validates URLs and sanitizes names; `hexciri-theme-set` dereferences symlinks (`cp -rL`) so symlinked extras apply correctly. The dead `Config ▸ Scripts` entry (opened nothing) is gone, and the Themes menu is back to pure selection (`Theme list / Palette source / Backgrounds`) — no duplicate Sync-vs-Update rows.
- **Nautilus theme stops flattening other apps**: `theme-set.d/10-gtk.sh` now scopes its state rules to `nautilus-window` and only emits them when Nautilus is installed. The imported nautilus theme was stamping global `window button:checked/active` (accent-filled square pills) and `window …row:selected` (near-invisible 15% accent tint) selectors into `gtk-4.0/gtk.css`, which load above app stylesheets and flattened the checked state and file-selection highlight of every other GTK app — Strata's release-channel and 1/2-click pills lost their selected fill, selected rows went faint. Other apps keep their own checked/selected styling now; Nautilus's flat look is unchanged.
- **Strata selections stay visible**: Strata's theme token `highlight` was the palette's raw selection shade, which on this dark scheme sits almost at surface luminance — its checked states (release channel, 1/2-click activation, selected rows) used to render as a pill you could barely tell from the background. The Strata theme now derives `highlight` by blending the selection color toward the accent, so checked controls read as a clearly raised indigo instead of vanishing.
- **System menu grows the Omarchy-maintenance set**: `System ▸ Maintenance` adds Reset boot config (`hexciri-refresh-boot` — re-runs the sync that keeps systemd-boot entries/PAM/menu curated; the stand-in for the plymouth reset), and `System` gains `Windows product key` and `Reset defaults`. `hexciri-windows-key` is a dual-boot convenience: it prints the OEM Windows key before you overwrite a previously-Windows machine, reading the MSDM ACPI table or the OA3 MSDM EFI variable, with an SMBIOS OEM-strings check and a full ACPI-table sweep as fallbacks for older BIOS builds that park the key in a non-MSDM/SLIC location. `hexciri-reinstall` re-runs the full install, then resets hexciri-owned configs to shipped defaults with backups, optional reboot. The rest of Omarchy's set was deliberately not ported — no drive-encryption-password (plain-root, no LUKS), no tmux config reset (tmux not shipped): nothing that isn't a live feature gets a menu row.
- **Discord channel highlight is readable again**: the ClearVision "Hexciri" theme picked near-white selected-channel text on ClearVision's main-color pill, which vanishes on pastel accents (white on `#99CEEF`). The hook now measures accent brightness and flips the selected text (and the invite/action icon, which ClearVision hardcodes to the light main-color) to the darkest palette shade on light accents, white on dark ones — the same luma idiom the System24 hook uses.
- **Quiet updates**: `hexciri-update-hexciri` (Repo sync / Hexciri) output is now just "syncing…", "pulling N commits…", "up to date" or "repo updated to x (…)"; the deploy runs silently and prints only on failure. `hexciri-update-run` no longer appends "(kernel … current)" to the done line — kernel info only surfaces when the boot-pinned kernel actually differs from the running one (reboot offer).
- **Updates are updates, not reinstalls**: `hexciri-update-hexciri` now just pulls new commits and deploys the changed files. install.sh gains `--update`: it skips every first-install-only step — pacman/channel/keyring, curated packages + AUR, zram, cache hook, service enables, PAM/keyring pin, SDDM greeter, GTK/audio/theme seeding, strata and the GPU/driver setup. Personalization (kernel, services, greeter, enabled units, seeds) is never re-asserted, and config deploys stay sha-tracked so your edits are kept. Up to date → "hexciri is up to date" and it stops; a plain install is unchanged.
- **Kernel choice survives re-runs**: `hexciri-gpu` no longer installs `linux`+`linux-headers` or flips the boot default to stock when run without `--kernel` on a machine that already picked a custom kernel — it resolves the pinned boot entry (bore/omarchy/lts/muqss/stock) and keeps it. Fresh installs with no pin still default to stock; foreign boot defaults are left untouched.
- **Fix a latent dispatcher bug**: plain `install.sh` re-exec wrongly forwarded `--dry-run`/flags on every run (`${VAR:+x}` fires on any non-empty value, so `false` triggered it); flags are now built explicitly, so a fresh plain install really does install and `--update` runs only when passed.
- **Learn menu**: new `Learn >` submenu in the root menu — official docs for the tools Hexciri ships (Hexciri site, Niri wiki, Noctalia docs, kitty, fish, Zed, OpenCode, Arch wiki, Starship), each opened in the default browser via `hexciri-launch-webapp`. Root menu reordered: Learn, Packages, Share, Capture, Reminders, Hardware, Themes, System, Restart, System Update.
- **Discord theme regenerates correctly**: the dynamic theme no longer reinstalls a stale cached file — it regenerates on every hook run unless a theme ships its own `vencord.theme.css`.
- **Nautilus follows the theme**: `theme-set.d/10-gtk.sh` stamps omarchy-nautilus-theme overrides (flat corners, themed headerbar/sidebar/pathbar/scrollbars/inputs, `@headerbar_border_color`) plus the system font into `gtk-4.0/gtk.css` and restarts `nautilus` on theme switch; a new `font-set.d/10-nautilus.sh` re-stamps the font when `hexciri-font` changes it (`install.sh` deploys `font-set.d`).
- **Discord picks up two themes**: the hook set now ships a ClearVision-based "Hexciri" theme (`vencord.theme.css`, colors + wallpaper live from the active palette/state) that coexists with the System24 one (`11-discord-system24` now writes `vencord-system24.theme.css`) — toggling either in Vesktop no longer clobbers the other.
- **Icons that exist on Arch**: real 512px `imv`/`imv-dir` icons are bundled under `branding/`, deployed to hicolor (`gtk-update-icon-cache`), and the media entries point at them; HP Scan's stock entry is shadowed with an icon Arch actually ships. `image/*` is pinned to imv so pictures open in the viewer, not a browser.
- **Gaming**: the Gaming category moves under Packages > Install (`Install ▸ Gaming`); its actions run in a held terminal and notify when Battle.net isn't installed; the Battle.net entry gets a real icon instead of a blank tile.
- **Missing package**: `noto-fonts-emoji` now ships by default — no more tofu in browsers/Discord from the start.
